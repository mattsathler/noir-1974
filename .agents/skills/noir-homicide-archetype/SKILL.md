# Noir homicide archetypes

Use this skill when adding a new kind of procedurally generated homicide or extending an existing homicide archetype in Noir 1974. It guides implementation through the existing generator and its dependent game systems; it does not authorize database resets, production data changes, or unrelated redesigns.

## Current design map

Read the relevant source before editing; this map describes the current implementation and may drift:

- [`apps/api/internal/cases/generator.go`](../../../apps/api/internal/cases/generator.go) owns `Definition`, candidate/evidence structures, the `archetypeGenerators` registry, deterministic archetype and candidate selection, shared validation, archetype-specific candidate builders and validators, plus case mail and financial-extortion record hooks.
- Archetypes currently registered are `workplace_conflict`, `jealousy`, and `financial_extortion`. The last is easy to miss: it reuses employment candidates but adds its own motive, evidence, bank/GATE records, emails, and validation. Do not describe the game as having only two archetypes.
- The registry pairs an ID with candidate generation, a validator, and required evidence types. `availableArchetypes` filters out archetypes with no candidates; generation picks among available archetypes first, then picks a candidate within the selected archetype. Preserve this two-stage selection so an archetype with many combinations does not dominate one with fewer.
- Shared validation checks the case seed, generator version and ID, homicide type, distinct existing victim and killer, existing crime location, valid world relationships, archetype-specific consistency, reachable evidence, required evidence types, and linked-record integrity. Keep archetype-specific world rules in their own validator.
- Evidence is assembled from `evidencePlan` values by `buildEvidence`; clues reference the case location, relationship IDs and participant IDs. Their internal classification stays server-side.
- [`apps/api/internal/cases/store.go`](../../../apps/api/internal/cases/store.go) loads embedded interrogation dialogue and residential-search findings by archetype ID. A new archetype may therefore need `interrogation/<id>.json` and `residential_search/<id>.json`; inspect the consumers and JSON structures before adding these files. Missing case-specific residential findings currently fall back to ordinary inventory, but an archetype-specific file is the established extension point.
- Case-specific emails are generated in `buildCaseEmails`; only some archetypes have tailored copy. Case-specific activity records are generated and validated through explicit hooks in `Generate`, `validateExtortion`, and `validateCaseRecords`. Mail and records are optional for a new archetype unless the story needs those evidence channels.
- [`apps/api/internal/cases/generator_test.go`](../../../apps/api/internal/cases/generator_test.go) covers determinism, references, solvability, invalid definitions, and an extortion-specific record chain. [`scheduler_test.go`](../../../apps/api/internal/cases/scheduler_test.go) covers recurring generation and participant reuse. Extend tests at the level of each new behavior.
- [`docs/architecture/casos.md`](../../../docs/architecture/casos.md) documents the archetype model and public/private information boundary. [`docs/architecture/registros-investigativos.md`](../../../docs/architecture/registros-investigativos.md) documents linked records.

## Workflow

1. **Define the story as a world-derived hypothesis.** State the motive, relationship or other world facts that make the participants plausible, the crime location rule, and the chain of clues by which a player can infer what happened. Decide which facts are required and which are optional. Do not invent NPCs, companies, relationships, locations, or facts that the world cannot support.
2. **Check candidate availability and balance.** Identify the existing relationship/entity types needed and how many valid candidates representative generated worlds produce. Reject self-pairs, missing entities, incompatible regions, absent locations, and reused participants where the caller excludes them. Sort map-derived IDs and any other unordered inputs before deterministic selection. Return no candidates when the world cannot support the story; do not silently fabricate a fallback.
3. **Add the archetype through the registry.** Give it a stable snake_case ID, candidate builder, dedicated validator, and required evidence types. Put its candidate logic and validation in focused functions. Avoid embedding its requirements into `validateWorkplaceConflict` or another unrelated archetype. If common structure is actually shared, extract the smallest reusable helper without changing existing behavior.
4. **Keep shared checks shared.** Produce a normal `Definition` with `CaseType == "homicide"`, distinct victim/killer, an existing location, explicit relationship references and clue evidence. Let common `Validate` check shared invariants; the new validator should verify that the referenced relationships and location genuinely support this archetype. Keep hidden classifications and solution links out of player-facing JSON.
5. **Connect only the narrative channels the story needs.** Add tailored dialogue at `interrogation/<id>.json` and contextual search findings at `residential_search/<id>.json` when relevant. Add email copy, bank/GATE records, or other data only if the archetype's clue chain uses that channel. Wire optional behavior explicitly and validate its case/NPC/role/timing links. Preserve everyday content and avoid marking clues as clues in the public presentation.
6. **Protect deterministic generation and version compatibility.** Check the current case generator version and every generation/reconstruction path before changing candidate sets, index inputs, evidence plans, messages, or record algorithms. Any change that can alter output for an existing seed/version requires a versioned strategy that preserves prior reconstruction; do not merely increment the constant or rewrite old output. If compatibility is not implemented, stop and report the gap instead of claiming old cases still reconstruct. Keep world-generator version handling distinct from case-generator version handling.
7. **Add behavioral tests with explicit fixtures.** Cover candidate eligibility and ineligibility, correct archetype selection, repeated seed/version output, participant exclusion, validator rejection of inconsistent relationships/location, clue reachability and required types, and each optional mail/record/search/dialogue connection. Assert that private culprit/classification fields are not exposed in public responses. Use deterministic seeds or fixture construction to target the archetype rather than relying on a flaky random sample.
8. **Update the architecture notes.** Add the new stable ID and its world prerequisites, clue channels, and versioning implications to `docs/architecture/casos.md`; update other architecture docs only for channels whose behavior or schema actually changed. Report touched files and validation evidence. Do not run tests unless the user asks for verification; when asked, run the Go API suite from `apps/api`.

## Design constraints

- A generated case must remain solvable from evidence reachable through the game's actual investigation flows. A motive or relationship alone is not enough; ensure the clues support a fair inference without exposing the answer directly.
- Preserve the distinction between a clue's player-facing presentation and its backend classification, relationship references, reachability and case links.
- Keep case type as homicide unless the user explicitly changes the product model; a new motive belongs in `ArchetypeID`, not a new `CaseType` by default.
- Do not add unrelated endpoints, schema changes, database mutations, or frontend mechanics just because the story could use them. Identify a missing prerequisite and report it if the existing world model cannot represent the requested plot.
- `generator.go` currently has some ID-specific conditionals for emails and records. When adding another specialized channel, prefer a narrow explicit strategy/hook that keeps the new archetype independent; avoid turning the generator into a growing switch over all archetypes or broad refactoring unrelated to the requested case.
