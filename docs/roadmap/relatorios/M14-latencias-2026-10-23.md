# M14 — Relatório inicial de latências

**Coleta:** 23/10/2026, horário de São Paulo  
**Ambiente:** API local em `127.0.0.1:8080`, conectada ao banco QA  
**Carga:** uma sessão temporária de QA; chamadas sequenciais por conexão HTTP persistente

## Resultados

Cada rota recebeu cinco chamadas de aquecimento e 40 amostras medidas. Todas as 40 amostras de cada rota terminaram com HTTP 200.

| Rota | Amostras | Mín. | p50 | p95 | Média | Máx. |

Percentis usam o método *nearest rank* sobre as amostras de cada rota. Os tempos são medidos pelo cliente e incluem o processamento HTTP completo, acesso ao banco e serialização da resposta.

## Leitura dos resultados

- A busca de NPCs é o alvo prioritário: sua mediana ficou entre 5 e 9 vezes acima das outras rotas medidas, e o p95 ultrapassou 6 segundos.
- A listagem de casos ficou em segundo lugar na mediana, com picos isolados de até 5 segundos.
- As demais rotas tiveram medianas entre 348 e 533 ms. Também apresentaram picos de até 3,1 segundos, compatíveis com variabilidade de rede ou do banco QA.
- A coleta foi serial e não mede capacidade sob concorrência. São 40 amostras por rota: suficientes para priorizar investigação, mas ainda uma linha de base inicial.

## Método e limites

- As seis rotas foram alternadas em ordem pseudoaleatória fixa para distribuir a carga no tempo; houve cinco rodadas de aquecimento antes das 40 rodadas medidas.
- Todas as chamadas usaram a mesma sessão temporária e a mesma conexão HTTP persistente. A única operação de escrita indireta foi a busca de NPCs, que registra descobertas para a conta temporária de QA; as leituras restantes não alteraram progresso do jogador.
- O arquivo [CSV bruto](M14-latencias-2026-10-23.csv) contém as medições de aquecimento e as amostras, com status e duração em segundos. A conta `m14perf20261024` foi criada exclusivamente para esta coleta; sua sessão foi revogada ao final.
- `/metrics` confirmou as chamadas e os status. O recorder atual mede duração por rota HTTP, mas ainda não mede duração nem quantidade de queries SQL por requisição. Portanto, este relatório prioriza endpoints; não atribui os tempos a uma query específica.
- Não houve comparação antes/depois com a otimização da busca ou com o lote de funcionários de email. O processo da API que serviu esta coleta não expõe um identificador de build, então estes números devem ser tratados como referência exploratória, não como prova de ganho da alteração.

## Próximo alvo da M14

### Diagnóstico inicial por query

O recorder agora mede queries `pgx` por rota e operação/tabela, sem registrar SQL, argumentos ou dados pessoais. Em uma busca de NPC antes da otimização do filtro, `select_world_entities` levou **2,51 s** de um total HTTP de **5,82 s**. A chamada executou dez queries SQL instrumentadas.

O filtro de `CityWorldForCases` foi alterado de `region_id LIKE 'cidade/district/%'` para igualdade contra os IDs dos distritos da cidade. Em 11 chamadas após a alteração, `select_world_entities` somou 4,54 s, média de **413 ms** por query. A média HTTP dessas 11 chamadas foi **4,03 s**. Essa comparação indica melhora forte nessa query, mas não isola efeitos de cache/rede nem comprova melhora p50/p95 do endpoint.

Na coleta, o fluxo completo chamava `SearchNPCsInCity` com a cidade da localização do jogador, portanto os 3,06 s de p50 representam uma busca municipal, não uma varredura global. Depois dessa coleta, o escopo funcional foi ampliado para o país da localização: a API gera apenas as cidades daquele país e filtra a busca por essa jurisdição; a interface da delegacia informa o país pesquisado. A linha de base acima não é comparável diretamente com essa busca nacional. É necessário coletar uma nova linha de base com a versão atualizada antes de avaliar o desempenho do escopo país.

A geração determinística das cidades nessa busca agora é mantida em cache por até 10 minutos, limitada a 16 escopos e invalidada por seed ou versão de geração diferente. O cache não contém status, NPCs expandidos ou relações persistidas. A API local estava indisponível durante essa alteração, então o efeito de latência ainda não foi medido; o cache deve ser avaliado com uma nova coleta após reiniciar a API com esta versão.

O mesmo perfil revelou duas leituras de `player_locations` por busca. `searchNPCs` agora reutiliza o `cityID` já resolvido ao consultar cenas dos casos. Uma chamada após a mudança registrou uma leitura de localização e respondeu em 5,48 s; nessa amostra, `select_world_mutations` levou 1,36 s, demonstrando a variabilidade entre chamadas.

Após o filtro por IDs de distrito, o endpoint fez em média aproximadamente quatro segundos por chamada nas medições curtas; a meta P0 ainda não foi validada. Repetir a bateria de pelo menos 100 amostras no mesmo processo atualizado antes de atribuir um ganho à rota. A geração determinística e a montagem do mundo seguem como possíveis fontes de custo, além do tempo de queries.

Uma busca após reutilizar o `cityID` registrou nove queries: uma a menos que o perfil inicial. `select_player_locations` passou de duas execuções para uma. Essa chamada levou 5,48 s; `select_world_mutations` foi a query mais lenta nessa amostra, com 1,36 s. O custo HTTP restante inclui trabalho fora das queries instrumentadas, como geração e montagem dos resultados.

Uma chamada diagnóstica a `GET /api/cases` respondeu em 726 ms e executou três queries: `select_player_sessions` (216 ms), `select_player_locations` (152 ms) e `select_cases` (152 ms). É uma única amostra e não substitui a linha de base de 40 medições.
